# Architecture

This page holds the technical detail that used to live in the README. For the short version, read
the [README](../README.md). For an interactive picture, open the
[architecture map](architecture/index.html) (a single offline HTML file).

## The pieces

| File | What it is |
| --- | --- |
| [`dagger.json`](../dagger.json) | Declares the Dagger module, pins the engine to `v0.21.8`, and lists the files the module needs to load. |
| [`.dagger/src/portfolio_delivery_dagger/main.py`](../.dagger/src/portfolio_delivery_dagger/main.py) | All the real code: one class with six functions (under 100 lines). |
| `.dagger/sdk/` | The Dagger Python SDK, vendored and generated by Dagger. Not handwritten; excluded from lint, type checks, and size limits. |
| [`pyproject.toml`](../pyproject.toml) | Dev tools (Ruff, mypy, Xenon, pytest, pip-audit) and the `poe` task names the checks call. |
| [`.github/workflows/dagger.yml`](../.github/workflows/dagger.yml) | CI. It only installs Dagger `0.21.8` and runs `dagger check`. Every action is pinned to a full commit SHA. |
| [`tests/`](../tests) | Contract tests for the module and the README. |

## Functions

| Function | Returns | What it does |
|---|---|---|
| `build` | `Directory` | Returns the files needed to load the module elsewhere: `.dagger/`, `LICENSE`, `dagger.json`. |
| `lint` | `Container` (check) | Ruff lint and format check. |
| `typecheck` | `Container` (check) | Strict mypy. |
| `complexity` | `Container` (check) | Xenon, every block must be grade A. |
| `unit` | `Container` (check) | The pytest tests not marked `integration`. |
| `publish` | `str` (image reference with digest) | Puts the `build` output in an image and pushes it with Dagger's own `Container.publish`. The password is a Dagger `Secret`, so it never shows up in logs. |

The four checks run inside a `python:3.13.14-slim` container pinned by digest. It installs
`uv 0.8.24`, runs `uv sync --frozen`, then the matching `poe` task. A Dagger cache volume keeps
uv's download cache between runs.

Each function asks the workspace for only the files it needs. `build` sees `.dagger/**`,
`LICENSE`, and `dagger.json`. The checks see the source, the SDK, the tests, the workflow file,
`pyproject.toml`, `uv.lock`, the README, `CHANGELOG.md`, `LICENSE`, and `docs/`. So an edit
to the README does not change the `build` output, and a code change does not bust caches it
does not affect.

### Known problem with `publish`

`publish` starts from `dag.container().from_("scratch")`. `scratch` is not a real image on
Docker Hub, so the call fails before it pushes anything:

```text
Error: failed to resolve image "docker.io/library/scratch:latest" (platform: "linux/arm64"): docker.io/library/scratch:latest: not found
```

An empty Dagger container is `dag.container()` with no `from_`. No test pushes an image, so
nothing caught this. The only publish test checks that `--password` is typed as a `Secret`.

## Why it is built this way

An earlier version of this repo was a custom release framework: stage objects, ports,
repositories, an ORAS client, and a workflow generator. Dagger already does most of that:
running steps as a cached graph, typed files and directories, secrets, services, pushing
images, checks, and traces. Rebuilding it made the code hard to use and maintain, so version
0.2.0 deleted it (see the [CHANGELOG](../CHANGELOG.md)).

The rules the module follows:

- Each function gets only the workspace files it needs.
- Checks run with `dagger check`, the same way locally and in CI.
- Functions are things a person wants done (build, publish), not internal stages.
- Functions return Dagger's own types (`Directory`, `Container`, `Secret`) so callers can keep
  chaining them.
- Pushing an image is left to Dagger's `Container.publish`.

GitHub Actions only starts `dagger check`. There is no delivery logic in the workflow file.

## Reuse before writing code

Before adding code:

1. Check Dagger's core types and functions.
2. Search the official Dagger modules and toolchains.
3. Search maintained modules from the wider ecosystem.
4. Write custom code only with a written reason and a test for the behavior.

Examples of built-in replacements: `Workspace.directory` for picking source files, `@check`
for validation, `CacheVolume` for tool caches, `Secret` for credentials, `Service` for
dependencies, `Changeset` for generated edits, and `Container.publish` for pushing images.

## Size limits the tests enforce

- Handwritten production Python: at most 400 lines (aim for 300 or fewer).
- Handwritten Python tests: at most 800 lines.
- The GitHub workflow: 15 to 30 lines, with every action pinned to a 40-character SHA.
- The generated Dagger SDK and lock files do not count.

A change gets rejected if it adds a custom type that copies a Dagger core type, wraps a single
Dagger call, adds a controller to ordinary CI, redoes Dagger's caching or secret handling, or
cannot show why a built-in feature or maintained library is not enough.

## What the module does not try to be

Dagger's cache is not a permanent record of releases across runs. If a future need really calls
for coordinating releases across several repositories (for example, "only one repo may publish
version X"), that service should be optional, separate, and justified by real users. Checking,
building, and publishing do not depend on one.

## Tests

- [`tests/test_modern_dagger_contract.py`](../tests/test_modern_dagger_contract.py): the module
  lists the six functions and four checks, the build output has exactly three entries and is
  byte-for-byte repeatable, the README and tests are left out of it, `publish` types its
  password as a `Secret`, the workflow is thin and pinned, and the size limits hold. Most of
  these are marked `integration` because they call the real `dagger` CLI at
  `/usr/local/bin/dagger`. CI does not run them (see [Getting started](GETTING_STARTED.md)).
- [`tests/test_readme_contract.py`](../tests/test_readme_contract.py): the README opens by
  saying who it is for, keeps its sections in order, links docs that exist, avoids internal
  jargon, and states the real engine version and function names.
